# Preparatory 15 minute recovery-point objective

This unit implements a synthetic metadata evaluator and local alert integration, not a live backup scheduler or hosted RPO certification. Run `node --test tests/platform/recovery-point.test.mjs tests/platform/monitor.test.mjs tests/platform/backup.test.mjs`. No provider/account/key is contacted or created.

The desired objective is900 seconds. A recently finished job does not establish a recoverable point. The evaluator uses the oldest covered timestamp across database, Auth, private Storage bytes and metadata, public configuration and secret references. Enabled n8n also requires its DB/config. Every component must name one coherent restore-set digest and exact software source, with authenticated readback, empty-target restore, offsite readback and key-custody evidence. These fields are injected synthetic evidence only until an independent provider adapter is accepted. Missing components, timestamps in the future, mixed checkpoints, unverified proofs and age over900 seconds block the sample. Boundary900 seconds is within the desired objective;900 seconds plus one millisecond is overdue. Only fixed component/error/metric labels reach the existing local alert sink; notifications and production authority remain unproven.

The future provider probe should fetch verified recovery-window and last committed transaction/WAL metadata, match the object/config restore set and hashes, measure probe age and alert on missing/unavailable/overdue evidence. An old PITR point can occur during database inactivity; an overdue timestamp is a conservative investigation signal, not proof of actual lost transactions. Confirm the last durable transaction watermark before interpreting data-loss exposure. Never replace this with job success time or an assumed cadence. Proposed probe cadence60 seconds is versioned in `infra/platform/recovery-point-objective.json`; no schedule is installed.

As checked2026-10-09, [Supabase official backup documentation](https://supabase.com/docs/guides/platform/backups) describes daily paid-plan backups, optional PITR for Pro/Team/Enterprise with at least Small compute, and separate handling for Storage object bytes and custom-role passwords. Database/PITR backup metadata alone cannot satisfy the complete CRM recovery contract. Final plan, retention, region, KMS/offsite ownership and alert destination require company decisions; current plan behavior must be rechecked before purchase or activation.

Incident sequence: block promotion; check provider/clock/last transaction metadata; authenticate/read back the selected recovery set; identify missing Storage/config/key coverage; notify the approved company destination; rehearse on an empty disposable target with actor/tenant/grant/Storage/login/revocation controls. No automatic destructive restore or credential rotation. Measure actual recovery duration and maximum supported data size in the final infrastructure; local test timing does not establish hosted RTO/RPO.
