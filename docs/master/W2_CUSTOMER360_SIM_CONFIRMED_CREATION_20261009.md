# W2 — SIM/eSIM creation waits for a confirmed current read

The previous SimCreate callback closed its drawer and refreshed the customer immediately after the sim.create receipt. It did not read the created SIM first. The existing reviewed-command hook already supports receipt retention and read-only recovery, so this unit supplies the missing confirmed read without changing the hook or its other consumers.

After the normal cookie-backed sim.create receipt, the creator caches that receipt and its reviewed input. It reads sim.get and verifies id, customer, operator, kind, display label, manual source and a version at least as recent as the receipt. Only that successful read closes the drawer and refreshes inventory/Customer360 summary. The resulting notice links to the actual read id. The creator is used by both Customer360 and the workspace inventory; their existing customer and role restrictions remain.

An uncertain command retries the frozen input/command_id through the existing hook. Once a receipt has been confirmed, a failed read leaves the creator locked and offers only Actualizar lectura. That action issues sim.get again, not another sim.create. No optimistic counter, assignment, activation, ICCID/EID or provider effect is introduced. The backend remains the authority for current status and permissions.

The existing sim lifecycle browser case is extended after every original action and assertion. A new helper commits through the real command route, drops only that response, replays exactly the same input and injects only a503 for the created SIM read. It requires SQL+1, no premature close/notice/KPI, locked fields and zero further writes during read-only recovery. It then checks the actual sim.get and customer360.summary bodies, collection record, prepared version1/no association/no activation, and whole-record/six-field visibility at1440/768/390. Viewer customer collection remains readable without creation. Original107 named cases and all prior lifecycle actions/assertions remain.

A focused sequential native Chromium reproduction uses actual old/new SimCreate, unchanged useReviewedCommand and ConfirmDialog, production React19 and actual sim input/result validators. Presentation/provider/operator adapters and a synthetic loopback in-memory command store are explicitly substituted: no Auth, database or Supabase acceptance. Both command attempts use the same input and create one synthetic record. The previous source closes after the receipt with zero sim.get calls; the new source preserves locked fields after503 and closes only after two reads, without a third write. A valid-shaped read for the wrong customer is refused; a further read-only retry succeeds with three reads/two identical commands/one record. All three cases have zero page errors.
