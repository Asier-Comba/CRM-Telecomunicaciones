Machine inventory: docs/master/contracts/product-environment.json. It contains names, scope, required LOCALDEV/TEST/STAGING/PROD conditions, secret classification, validators, purpose and provider class; no environment values. Existing provider placeholders are explicitly reserved_future, not registered adapters. Validation never prints secret values, endpoints or credential payloads. node scripts/security/check-product-environment.mjs --environment TEST (or LOCALDEV/STAGING/PROD) validates syntax/required pairs only and returns safe names/codes. Public legacy JWT binding must declare anon, never service_role. Production platform/origin must use HTTPS and cannot use loopback. Valid config is not provider health or delivery proof.

Rebuild from an empty disposable environment uses the canonical migration directory, pinned supabase/config.toml, explicit private bucket declarations, automatic seeds OFF, private function privilege manifest, protected product catalog and synthetic fixture runners. The native fresh/restore oracle verifies every function ACL/definer flag and private forced RLS; real pinned CLI stack verifies migration head/count, actual Auth/PostgREST/Storage, current membership/revocation, exact bucket size/type/privacy and teardown. Config SHA-256 is retained as source fingerprint. Native PostgreSQL test and official local platform versions are reported separately, not treated as a hosted production exercise. No production/hosted environment is configured by this task; Issue #12 remains future staging evidence.

Document verifier setup requires an operator-installed private document_integrity_verifiers key matching server-only PRODUCT_DOCUMENT_VERIFY_KEY_ID/HEX. It is a purpose-specific MAC verifier, not a staging decryption key. No browser installer or generic product service-role worker is granted. CI generates a fresh key, installs it only in the disposable DB, passes it only to the ignored-output server process and tears down both. Key rotation/production secret-manager installation is operational work, not established by an env flag. Required production scanning blocks while no adapter exists.

Import staging production provider/principal/domain adapters remain unregistered. IMPORT_STAGING_ADAPTER=disposable-local and IMPORT_STAGING_TEST_KEY work only in a test process with an ephemeral test key; production must not use them. The local quarantine bucket remains private ZIP-only with no authenticated plaintext upload policy; the new CSV test adapter is separate encrypted filesystem staging. XLSX unregistered and ZIP processing blocked.

Auth email readiness is separate from CRM email. Auth SMTP requires an independently installed platform delivery adapter, approved sender/domain, HTTPS public site, exact callbacks and actual deliverability. CRM delivery requires its own registered adapter and private reference plus independently verified sender/domain and delivery. Current mail.readiness.v1 truthfully returns not_configured/unregistered/production_unverified for both; credentials or a configured=true flag cannot prove connection or successful email. Local fixture users are synthetically confirmed through admin setup, not mail delivery proof. No SMTP/API/OAuth provider was activated and no mail sent.

Verification includes three meaningful Node tests and real-local metadata drift/preflight observations. Browser bundle canaries include the document witness key and disposable import root key. Exact accepted source/run is recorded above; no production readiness claim is implied.
