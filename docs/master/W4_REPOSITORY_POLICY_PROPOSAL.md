# W4 repository protection proposal

This is a versioned proposal and validator, not an applied GitHub policy. It performs no administration, visibility, permissions or API write. Current protection must be verified independently; this file cannot declare the repository protected. Run `node scripts/ci/repository-policy.mjs` and `node --test tests/security/repository-policy.test.mjs`.

The proposal requires two independent approvals, dismissal after new changes, last-push approval from a different person, company CODEOWNERS and resolved review threads. Required checks retain all-ref history, full dependency/build quality, native restoration, real Supabase and platform image/recovery/vendor gates. No bypass actor, ref exclusion, force-push/deletion allowance or old-source acceptance is prepared. Normal merges preserve consumed parent provenance.

The pure renderer produces only a disabled ruleset payload after an independently verified Actions App ID is supplied; no real ID or reviewer identity is invented. Context-only checks can accept an unintended status producer, so the eventual API payload must bind every context to the verified app. Match `~DEFAULT_BRANCH` instead of assuming that this repository currently uses main. Required path-filtered workflows must report on the selected protected target or the rule will remain pending; adopt/verify their source before activation. The all-ref scanner in this unit runs on every PR, including Draft readiness, and still blocks unresolved candidates without exceptions.

The [official GitHub rules REST schema](https://docs.github.com/en/rest/repos/rules) defines branch conditions, status-check integration IDs, required reviews and disabled/active enforcement. Creating or activating a ruleset requires administrative write permission and explicit user authorization, which is outside this execution. Do not apply the renderer's output automatically or treat a disabled proposal as protection. Company reviewers/CODEOWNERS, MFA ownership, trusted app identity, plan feature availability and exact-target check reporting must be verified first. No administrative command is supplied.

GitHub visibility/organization ownership/SSO/MFA, team access, environment reviewers and fork/artifact retention need separately approved company settings. Do not add a blanket exception for currently failed security gates. W4 and W5 authored by one executor do not satisfy independent review. Next: review this proposal, resolve required gate outcomes, then obtain explicit administrative authorization before any applied configuration.
