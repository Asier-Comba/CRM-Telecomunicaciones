# Registered external identities — W2 backend takeover candidate

Human cookie route `/api/telecom/external-identities/v1` supports `external_identity.integration_register`, `bind`, `retire`, `integration_list` and `list`. All operations require a current owner/admin membership. PostgreSQL rechecks authority before command replay. The existing disabled-by-default product flag, canonical Origin/Host gate and no-store transport apply. No assistant tools or provider effects are registered.

Integration registration selects a closed provider class (`generic.telecom.v1`, `generic.crm.v1`, `local.import.v1`), a workspace-unique integration key, display label and declared import/integration source. Active registration means metadata mapping is available; every receipt and registry row states `external_effect: disabled`. There are no credentials, arbitrary endpoint URLs, OAuth sessions or health claims.

Bindings record workspace, integration, external kind/ID, local entity kind/UUID, declared source, status, version and timestamps. Fifteen existing root entity kinds are registered. The unique integration/external-kind/external-ID tuple cannot silently rebind; the local entity must exist in the same workspace. The database trigger enforces immutable context and source consistency. Twenty competing requests for two targets retain exactly one mapping; identical bindings reuse that resource. Retirement requires exact CAS, retains history and preserves prior command receipts. Retired slots cannot be reused for another target.

Owner/admin reads are independently bounded to1–100/default20 with UUID keysets and exact local-entity scope, optional integration/status filters. External IDs are private administrative mapping facts: no global search, ordinary row propagation, browser storage or telemetry. Audits contain only operation/resource/version. Both tables have forced RLS and no raw user/service-role table grants; only closed authenticated RPCs are executable. Internal helpers remain non-executable by application roles.
